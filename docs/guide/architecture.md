# Architecture

[Back to README](../../README.md)

How the code is laid out and how the parts fit together. The decisions behind
it are recorded in the [ADRs](#decisions).

## Project layout

```
index.html, css/        the page and its letterboxed canvas
src/main.ts             boot: screen, input, scenes, loop
src/loop.ts             fixed 60 Hz timestep
src/input.ts            keyboard to per-player actions, remapping
src/touch.ts            on-screen touch buttons to the same actions
src/gamepad.ts          gamepads to the same actions
src/audio.ts            procedural Web Audio voices, music and sound effects
src/voice.ts            the announcer: callouts spoken by the browser's speech synthesis
src/storage.ts          settings, controls, Personal Bests, High Scores
src/sim/                pure simulation (no DOM), in the original's pixels and frames
src/art/                code-defined pixel art: palette, kits, athletes, stadium, each Event's props
src/render/             drawing: screen scaling, pixel font, HUD, Mark display, each Event's renderer
src/scenes/             screens: title, menus, Event, results, High Scores, initials, Settings and so on
data/                   game data: Event parameters, Standards, Points, difficulty, Attract Mode playlist and demos
sw.ts, manifest.webmanifest, icons/   installable, offline PWA
build.ts                bundles and minifies the site into dist/ (served by pnpm start, deployed to Pages)
favicon.ico, browserconfig.xml        browser and Windows icons (generated by pnpm icons)
robots.txt, sitemap.xml, images/       search engines and the social sharing card
tools/                  development scripts (icons, sprite sheets, Attract Mode demos, colour-vision checks, size budget)
calibration/            Input Trace and Reference Mark formats, data, notes and the replay harness
test/                   node --test suites
docs/                   product requirements, ADRs, style guide, this guide and screenshots
```

`pnpm build` (`build.ts`) bundles `src/main.ts` and everything it imports,
the JSON data included, into one minified `dist/js/main.js`, which
`index.html` loads. The service worker is built likewise. See
[Development](development.md#building).

## The frame loop

`src/loop.ts` runs a fixed-step clock: the game advances in exact 1/60 second
steps however fast the display refreshes, and draws once per display frame.
Step boundaries are computed from the start time rather than by adding, so
they don't drift. Gaps longer than 250 ms (a background tab, a debugger
pause) are dropped rather than replayed as a burst.

Each step, `src/main.ts`:

1. polls the gamepads;
2. drains the input that happened before the step's end time (action edges,
   raw keys, raw pad buttons and taps);
3. steps the current scene with it;
4. shows the touch buttons the scene needs.

Then it renders the scene, and the FPS meter if `?fps` is in the URL.

## Input

Every device turns into the same **normalised actions**, per player:
`RUN_A`, `RUN_B` and `ACTION` for players 1 and 2, and `PAUSE`, `START`,
`UP`, `DOWN`, `LEFT` and `RIGHT` as shared actions (player 0).

- `src/input.ts`: the keyboard, by `KeyboardEvent.code`, with remappable
  bindings and the fixed menu keys. Each press and release is timestamped and
  queued until the step it falls in, so every press lands in exactly one
  frame and none are dropped.
- `src/touch.ts`: on-screen buttons. Layout and pointer tracking are plain
  functions, unit-tested in Node; `attachTouch` wires them to the DOM.
- `src/gamepad.ts`: polled once per step, with button changes stamped just
  inside the step.

The menus and the Controls and Key Test screens also get the raw keys, pad
buttons and taps. See [Controls](controls.md).

## Scenes

`src/scenes/manager.ts` holds one active scene at a time. A scene has
`enter`, `exit`, `suspend` (the page was hidden), `step` and `render`. A
change asked for during a step happens after the step, so a scene never runs
after its own exit.

| Scene | File | What it is |
|---|---|---|
| `title` | `title.ts` | Title art and theme; idles into the High Score table and Attract Mode |
| `menu` | `main-menu.ts` | Arcade, Practice, Two Player, High Scores, Settings |
| `practice` | `practice.ts` | Event picker with Personal Bests |
| `event` | `event.ts` | Plays one go at an Event: intro card, Attempts, HUD, pause menu, Session scoring |
| `results` | `results.ts` | The Event's Mark, Personal Best, Standard and Points; moves the Session on |
| `initials` | `initials.ts` | High Score initials entry |
| `highScores` | `high-scores.ts` | The High Score table |
| `attract` | `attract.ts` | Replays Input Traces through the simulations |
| `settings` | `settings.ts` | The Settings menu |
| `controls` | `controls.ts` | Remapping |
| `keyTest` | `key-test.ts` | Ghosting test |
| `cookiePolicy`, `credits` | `text-page.ts` | Scrolling text pages |

Shared pieces: `menu.ts` (the vertical menu every screen uses),
`catalogue.ts` (each Event's simulation, renderer and sounds),
`attempt-plans.ts` (how a go splits into Attempts: the three-Attempt series,
or the High Jump's rising bar), `event-sounds.ts`, and `services.ts`.

Scenes get storage, sound, settings, controls and the catalogue passed in as
**services** rather than importing browser globals, so the tests can run
every scene in Node with fakes. `index.ts` registers them all.

## Simulation

`src/sim/` is pure: plain data in, plain data out, no DOM. The same modules
run in the browser, in the tests and in the replay harness.

Each Event is a factory that takes its parameters and returns an object with
three functions:

- `init({ cycle, players, attempt, barHeight })`: the starting state;
- `step(state, input)`: one 60 Hz frame, given that frame's action edges;
- `getResult(state)`: `null` until the Attempt is decided, then its Marks
  (and the Rival's time in running Events).

| Module | What it does |
|---|---|
| `speed.ts` | The speed meter all Events share |
| `field.ts` | Angle hold, launch, flight and the Attempt series for field Events |
| `rival.ts` | The Rival's seeded pace per Cycle |
| `sprint.ts`, `long-jump.ts`, `javelin.ts`, `hurdles.ts`, `hammer.ts`, `high-jump.ts` | The six Events |
| `standards.ts`, `points.ts`, `session.ts` | Standards per Cycle, Mark to Points, and the Arcade Session |
| `difficulty.ts` | Applies Easy or Hard on top of the Normal parameters |
| `registry.ts` | The only sim module that reads `data/*.json`; builds every Event at every difficulty |
| `events.ts`, `types.ts` | Event ids in order, and shared types |
| `placeholder.ts` | A stand-in Event, used by the tests and listed in Practice only while a real Event is missing |

The simulation works in the **original's pixels and 60 Hz frames**, not
metres and seconds
([ADR-0004](../architectural-decision-record/0004-sim-in-original-pixels-and-frames.md)),
because that is how reference data is measured. Seconds and metres appear
only when a Mark is shown, in `src/render/marks.ts`, using the
`metresPerPixel` of each Event in `data/events.json`.

Because the simulation is a pure function of its inputs and steps at a fixed
rate, the same Input Trace always gives the same Mark. Pausing stops the
Event's frame counter too, so resuming carries on from the same frame. The
Rival's pace variation is seeded for the same reason.

## Rendering and art

The canvas is 320x240 internal pixels (`src/render/display.ts`), scaled with
`image-rendering: pixelated`. Normally it is letterboxed at the largest
whole-number scale that fits; in Full Screen it is stretched to fill the
screen (`src/render/screen.ts`).

- `src/art/` draws everything as code: the palette (`colours.ts`), the
  proportions and animation timing (`style.ts`), athletes, the stadium and
  crowd, and each Event's props. No image files are loaded.
- `src/render/` holds each Event's renderer, the shared HUD (speed bar,
  timer, Attempt counter, angle dial, Mark readout, foul banner), the 5x7
  pixel font and text drawing, the title art and the FPS meter.

Renderers read the simulation state and never change it. Sim pixels map to
screen pixels one to one, with a camera that follows the athlete.

The look is defined in the [style guide](../style-guide.md), and the tests
hold the art to it.

## Audio

`src/audio.ts` synthesises every voice with Web Audio at runtime: square-wave
and triangle melodies (the theme and the intro fanfare), a synthesised drum
kit, and the sound effects. Audio is unlocked from the first key press or tap,
because browsers only allow it inside a user gesture.

`src/voice.ts` is the announcer. The Event sound hooks and the scenes call
`sounds.say(id)` with a callout id from `data/callouts.json`, and the voice
speaks the phrase with the Web Speech API, following mute, volume and the
ANNOUNCER setting. There are no recordings. The starter's calls ("On your
marks", "Get set", "False start") interrupt anything still being said, so
they land on cue before the gun, and quitting to the menu or title, hiding
the page or closing it cancels speech at once.

When an Attempt is decided, the event scene holds on it before moving on
(`REACTION_FRAMES`, 1.5 s, after a pass; `FAILED_REACTION_FRAMES`, 4 s,
after a failure, so the head shake is seen before the next Attempt or GAME
OVER), passing renderers `after` (frames since it was decided)
and the `standard`. `src/render/reaction.ts` turns those into the athlete's
reaction, and the Long Jump renderer times its measurer by them. The
simulation has already stopped by then, so none of this can change a Mark.

## Storage

`src/storage.ts` keeps settings, controls, Personal Bests and High Scores in
`localStorage` under `hexathlon:*` keys, each in a versioned envelope. Every
access is guarded, falling back to an in-memory store, and bad data falls
back to defaults field by field. See [Settings](settings.md#what-is-stored).

## Data

| File | Used by |
|---|---|
| `data/events.json` | Every Event's parameters |
| `data/standards.json` | Standards per Cycle |
| `data/points.json` | Mark to Points |
| `data/difficulty.json` | Easy, Normal and Hard |
| `data/attract.json`, `data/attract/*.trace.json` | Attract Mode playlist and demo Input Traces |

The simulation loads the first four as JSON modules through
`src/sim/registry.ts`. The Attract Mode files are fetched at start-up.
